## 処理フローの3パターン

```
① 通常の機能追加（人間が主導）
   feature/xxx ブランチ作成
        │
        ▼
   実装 → push（ユーザー実行）
        │
        ▼
   PR作成 → ci.yml が起動（lint/test）
        │         └ claude-code-review.yml も起動（自動レビュー）
        ▼
   全チェックpass → マージ
        │
        ▼
   deploy.yml が起動 → GitHub Pagesへ自動反映

② Claude Codeへの自動依頼（@claudeメンション）
   Issueを起票し、本文かコメントに "@claude ○○して" と書く
        │
        ▼
   claude.yml が起動 → 内容を読み取り
        │
        ▼
   自動でブランチ作成・実装・PR作成
        │
        ▼
   （以降は①と同じ: CI確認 → マージ → 自動デプロイ）

③ リリース
   区切りの良いタイミングで
        │
        ▼
   gh release create vX.Y.Z --notes "..."
        │
        ▼
   タグ付きのGitHub Releaseが公開される
   （セマンティックバージョニング: 新機能=Y／修正のみ=Z）
```

## 認証まわりの注意点（複雑さの核心）

同じ「GitHub Actions上で動くワークフロー」でも、認証方式が2系統に分かれている点が最も分かりにくいポイント。

- **`GITHUB_TOKEN`系**（`ci.yml`／`deploy.yml`）: GitHubが各ワークフロー実行のたびに自動発行する、リポジトリ内で完結するトークン。追加設定不要。
- **`CLAUDE_CODE_OAUTH_TOKEN` + GitHub App系**（`claude.yml`／`claude-code-review.yml`）: `claude`という外部Botアカウントとして振る舞うための認証。Secrets登録に加えて、GitHub App（`github.com/apps/claude`）のインストールという、ブラウザでの同意操作が別途必要。

新しい自動化を追加する際は、まず「このワークフローは`GITHUB_TOKEN`だけで完結するか、それとも外部サービスとして動く必要があるか」を見極めると、必要な設定（Secrets／App導入の要否）を判断しやすい。
